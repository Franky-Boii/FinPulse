# FinPulse Data Module

## 1. Overview

FinPulse is built around e-commerce data.

The platform starts with operational data in PostgreSQL and transforms it into analytical data that can be used by the dashboard.

The basic flow is:

```text
Source Database
      ↓
Raw Data
      ↓
Staging
      ↓
Analytical Marts
      ↓
API
      ↓
Dashboard
```

---

# 2. Source Data

The source database contains five main tables.

```text
customers
products
orders
order_items
payments
```

These tables represent the information generated by an e-commerce application.

---

## 3. Customers

The `customers` table contains information about people who purchase products.

Important fields include:

| Field         | Description                  |
| ------------- | ---------------------------- |
| `customer_id` | Unique customer identifier   |
| `full_name`   | Customer's name              |
| `email`       | Customer email address       |
| `country`     | Customer's country           |
| `signup_date` | Date the customer registered |

Example:

```text
customer_id | full_name       | country
------------|-----------------|----------
1           | Thandiwe Mokoena| South Africa
2           | Liam O'Connor   | Ireland
3           | Aisha Bello     | Nigeria
```

---

# 4. Products

The `products` table contains the products available for purchase.

Important fields include:

| Field          | Description               |
| -------------- | ------------------------- |
| `product_id`   | Unique product identifier |
| `product_name` | Product name              |
| `category`     | Product category          |
| `price`        | Product price             |

Example:

```text
product_id | product_name              | category
-----------|---------------------------|------------
1          | Wireless Mouse            | Electronics
2          | Mechanical Keyboard       | Electronics
3          | USB-C Hub                 | Electronics
```

---

# 5. Orders

The `orders` table represents purchases made by customers.

An order connects a customer to a purchase.

Conceptually:

```text
Customer
   ↓
Order
```

An order contains information such as:

* Order ID
* Customer ID
* Order status
* Order timestamp

For example:

```text
order_id | customer_id | status
---------|-------------|----------
1001     | 25          | completed
1002     | 31          | completed
1003     | 25          | cancelled
```

---

# 6. Order Items

An order can contain multiple products.

This is why FinPulse has a separate `order_items` table.

```text
Order
 ├── Product A
 ├── Product B
 └── Product C
```

Important fields include:

| Field           | Description               |
| --------------- | ------------------------- |
| `order_item_id` | Unique item identifier    |
| `order_id`      | Order containing the item |
| `product_id`    | Product purchased         |
| `quantity`      | Number of units purchased |
| `unit_price`    | Price per unit            |
| `line_total`    | Quantity × unit price     |

For example:

```text
order_id | product_id | quantity | unit_price | line_total
---------|------------|----------|------------|-----------
1001     | 1          | 2        | 249.99     | 499.98
1001     | 3          | 1        | 349.50     | 349.50
```

The order contains two different products.

---

# 7. Payments

The `payments` table contains payment information associated with orders.

It allows FinPulse to understand whether an order was successfully paid and how much was paid.

This information is important when calculating revenue.

---

# 8. How the Tables Relate

The main relationships can be simplified to:

```text
customers
    │
    │ customer_id
    ▼
orders
    │
    │ order_id
    ▼
order_items
    │
    │ product_id
    ▼
products

orders
    │
    │ order_id
    ▼
payments
```

This means:

* One customer can have many orders.
* One order can contain many order items.
* One product can appear in many order items.
* An order can have payment information.

---

# 9. Raw Data Layer

The first layer in the warehouse is the **raw layer**.

The raw layer stores data from the source database.

```text
raw
├── customers
├── products
├── orders
├── order_items
└── payments
```

The purpose of this layer is to keep a reliable copy of the source data before applying analytical transformations.

---

# 10. Staging Layer

The staging layer prepares data for analytical modelling.

It is where data can be cleaned, standardised, renamed, or prepared before becoming final analytical models.

The idea is:

```text
Raw Data
   ↓
Clean / Prepare
   ↓
Staging
```

This separation makes the transformation process easier to understand and maintain.

---

# 11. Marts Layer

The final analytical models are stored in the `marts` schema.

FinPulse currently uses models such as:

```text
marts
├── dim_customers
├── dim_products
├── fact_orders
├── mart_customer_metrics
├── mart_daily_revenue
└── mart_top_products
```

These models are designed specifically for analytics.

---

# 12. Dimensions and Facts

FinPulse uses a simple analytical modelling approach.

### Dimensions

Dimensions describe entities.

Examples:

```text
dim_customers
dim_products
```

A customer dimension describes customers.

A product dimension describes products.

### Fact

A fact table records business events that can be measured.

```text
fact_orders
```

contains analytical information about orders.

This allows questions such as:

> How much revenue did we generate?

> How many products were sold?

> How many orders did a customer make?

---

# 13. Customer Metrics

`mart_customer_metrics` combines customer and order information to create useful customer-level metrics.

Examples include:

* Number of orders
* Total order value
* Total units purchased
* First order date
* Latest order date

For example:

```text
Customer
   ↓
Orders
   ↓
Customer Metrics
```

This allows the dashboard to show a summary of customer purchasing behaviour.

---

# 14. Daily Revenue

`mart_daily_revenue` aggregates order information by date.

Conceptually:

```text
Orders
   ↓
Group by date
   ↓
Calculate metrics
   ↓
Daily Revenue
```

The model provides metrics such as:

* Order count
* Revenue
* Units sold

Example:

```text
order_date  | orders | revenue
------------|--------|---------
2026-09-05  | 120    | 45000.50
2026-09-06  | 135    | 51200.25
```

---

# 15. Top Products

`mart_top_products` calculates product performance.

It can be used to determine which products generate the most revenue.

Conceptually:

```text
Orders
   +
Order Items
   +
Products
   ↓
Product Performance
```

The resulting model contains information such as:

* Product
* Category
* Units sold
* Revenue

This powers the product analytics in the dashboard.

---

# 16. Product Drill-Down

FinPulse also allows a user to investigate an individual product.

For example:

```text
Product
   ↓
Product Performance
   ↓
Sales History
   ↓
Recent Orders
```

For a selected product, the API can provide:

* Product information
* Units sold
* Revenue
* Number of orders
* Daily sales history
* Recent orders containing that product

This connects high-level analytics to the underlying transactional data.

---

# 17. Revenue Calculation

Revenue is based on successful sales rather than simply counting every transaction.

Cancelled orders should not contribute to sales metrics.

For product sales, FinPulse calculates:

```text
Revenue = quantity × unit price
```

For example:

```text
2 × R249.99 = R499.98
```

Multiple items can then be combined to calculate the value of an order or the total revenue for a period.

---

# 18. Data Transformation

dbt is responsible for transforming the warehouse data into analytical models.

The general process is:

```text
Source Data
    ↓
Raw Tables
    ↓
dbt Transformations
    ↓
Analytical Models
    ↓
FastAPI
    ↓
Dashboard
```

This means the frontend does not need to understand the complexity of the underlying database.

---

# 19. Data Quality

FinPulse also uses data tests as part of the transformation process.

The purpose of data quality checks is to catch problems such as:

* Missing required values
* Invalid relationships
* Duplicate records
* Unexpected data

The goal is to make sure that data reaching the analytical layer can be trusted.

---

# 20. Real-Time Data

Not all analytics go through the batch layer.

Some data is processed in real time:

```text
PostgreSQL
    ↓
Debezium
    ↓
Redpanda
    ↓
Spark
    ↓
Redis
```

Spark processes streaming events and produces real-time aggregates.

These are stored in Redis so that the API can retrieve them quickly.

---

# 21. Batch vs Real-Time Data

The two approaches have different purposes.

| Batch              | Real Time        |
| ------------------ | ---------------- |
| Airflow            | Debezium         |
| dbt                | Redpanda         |
| Warehouse          | Spark            |
| Analytical marts   | Redis            |
| Complete analytics | Recent analytics |

In simple terms:

```text
Batch     = reliable analytical view

Real-time = fast view of recent activity
```

---

# 22. Final Data Flow

Putting everything together:

```text
                         PostgreSQL
                        Source Data
                             │
               ┌─────────────┴─────────────┐
               │                           │
               ▼                           ▼
           Debezium                     Airflow
               │                           │
           Redpanda                    Warehouse
               │                           │
             Spark                        dbt
               │                           │
             Redis                       Marts
               │                           │
               └─────────────┬─────────────┘
                             │
                           FastAPI
                             │
                           React
                             │
                         Dashboard
```

The important idea is that FinPulse takes **raw business data** and turns it into **useful analytics** through a combination of streaming and batch processing.

---

## 23. Data Module Summary

The FinPulse data journey is:

```text
Capture
   ↓
Store
   ↓
Transform
   ↓
Model
   ↓
Serve
   ↓
Analyze
```

The source database contains the business data.

The warehouse stores and transforms that data.

dbt creates analytical models.

The API exposes the results.

The React dashboard makes the results easy to explore.

Together, these layers form the data foundation of FinPulse.
